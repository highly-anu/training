# Watches

Two watch apps run the same sessions: the Garmin Connect IQ app (`garmin/`) and the
Apple Watch app (`ios/TrainingCompanionWatch Watch App/`, relayed by the phone). This
document is how they are kept in step: the contract they share, the rule for a new
watch feature, and where each one stands. The ranked work is `docs/roadmap.md`
item 14; the Garmin layout and the add-a-philosophy walk-through are
`garmin/TrainingCompanionCIQ/README.md`.

## The rule

**A watch feature lands with its server key and both watches, in one branch**
(`watch/<feature>`). If one watch has to follow later, its row below says *pending*
and names the roadmap item. Platform-native work (the table's last section) is the
only exception.

## One contract

`GET /api/user/today-session?date=<watch's day>&spec=1&week=1` is what a watch reads
(`api.today_session`, `encode_watch_session`, `_encode_watch_exercise`). The Garmin
calls it with its `ciqdev_` token; the phone calls it for the Apple Watch and forwards
the body unchanged over WatchConnectivity (`WatchDayMessage`), and the watch decodes it
(`WatchDay`). The phone keeps no day logic of its own.

- A new feature starts as a payload key, pinned in `test_today_session.py` or
  `test_watch_spec.py`. `?spec=` only adds keys; a build that does not know one ignores it.
- **The server writes the words and the numbers** — `loadDescription`, `last`,
  `standard`, `progress.headline`, `tomorrow`. Neither watch formats what the server can.
- Uploads go through the same two routes from both watches: `POST /health/workouts`
  and `PUT /health/sessions/<key>`, keyed by exercise id (`garmin/core/source/engine/Wire.mc`,
  `ios/TrainingCompanion/WatchUpload.swift`). The Apple Watch hands its session to the phone
  live while the phone is reachable; the phone stores it and answers `stored`, and only
  without that answer is the copy queued (`WatchUploadMessage`). Queued alone, a workout
  reached the server whenever the system delivered it — between simulators, never.

## One vocabulary

`data/commons/watch_vocabulary.json` lists the templates, fields, title parts, lines,
LAP actions and behaviours; each package's `watch.yaml` picks from it and
`src/watch_spec.py` resolves it into the payload's `screens`. Nothing in either
watch's renderer names a philosophy or an archetype (`garmin/tools/check_core_neutral.py`).

An id is added to the JSON and implemented on both watches in the same change. The
Garmin's renderer is `garmin/core/source/spec/SpecRenderer.mc` (with `Vocab.mc`
generated by `garmin/tools/gen_vocab.py`); the Apple Watch's is `ios/TrainingCompanion/WatchSpecText.swift`,
over `WatchVocab.swift` (generated by the same tool), whose switches are exhaustive: an id
added to the JSON does not build until the Apple Watch draws it. `Views/StepPageView.swift`
draws every step with it (design-system §9.6).

## Where they stand

As of 2026-10-18. *Server* is the payload key; *—* means the server has no part.

| Feature | Server | Garmin | Apple Watch |
|---|---|---|---|
| Today's sessions | `sessions` | yes | yes — the day relayed as it is |
| Screens by template (package `watch.yaml`) | `screens`, `screen` | yes | yes — the same data page (`StepPageView`) |
| Done today, on any device | `completed` | yes | yes |
| Last time per exercise | `last` | yes | yes |
| Test step: best and the next level, Save results / Not a test | `standard` | yes | yes |
| Week progress | `progress.week` | glance, Progress page | This Week count, complication ring |
| Programme %, headline, trend | `progress.program`, `.headline` | Progress page | Progress page (Today ▸ Progress) |
| Week ahead | `days` (`week=1`) | Week menu | Week page: days → sessions → steps |
| Tomorrow on a rest day | `tomorrow` | yes | yes, and once the day's sessions are done |
| Readiness | `readiness` | ring | dot and score |
| Program not started yet | `status`, `startsOn` | not checked | "Starts Mon 20 Oct" |
| Max HR for the zone alerts | `maxHR` | — (the watch's own zones) | yes |
| Sync failure in words | — | yes | Sync row: "ok 07:41" / "failed 07:41 · No phone" (`WatchListText`) |
| Edit set before, next and after; pace | — | yes | Set Next and Edit Set (commands page, carried forward); pace edit and the pre-start plan pending |
| Metronome | `targetRpm`, `metronome_rpm` | yes | yes: a haptic beat while paced, switched on the commands page |

| Double bells | `bells` (exercises.yaml) | 2x24 and both bells in the volume | the same; neither watch reads it off the id any more |
| Upload: sets by id, rounds, clock, distance | — | `Wire.mc` | `WatchUpload` |
| **Native, not shared** | | glance (64 KB), wellness posting, pairing QR | HealthKit workout and route, complication, overtime prompt |

## Tests

| What | Server | Garmin | Apple Watch |
|---|---|---|---|
| Payload | `test_today_session.py`, `test_watch_spec.py`, `test_last_time.py` | — | `WatchDayTests` on `data/watch_day_fixture.json` (route-written) and the demo sessions |
| Generated files current | `test_watch_spec.py` (`gen_vocab --check`, `check_core_neutral`) | — | — |
| Rendering | — | `SpecFixtures.mc` on `data/watch_fixtures.json` (`build.sh --test`, simulator open) | `WatchSpecTests` on the same file |
| Upload shape | — | `WireTests.mc` | `WatchUploadTests` |

`data/watch_fixtures.json` is the screens' contract: a server-shaped exercise, its spec
and the engine's state in; the title, the two fields, the gauge field, the two lines and
what LAP does out. `WatchSpecTests` runs it through `WatchSpecText` and checks every
vocabulary id is drawn by some case; `garmin/tools/gen_spec_fixtures.py` turns it into
`garmin/core/test/SpecFixtures.mc`, which runs it through `SpecRenderer`. Change a screen
in the JSON, never in one renderer. Swift logic the tests should reach goes in a file
both the app and the watch compile (the watch target's membership exceptions:
`WatchModels.swift`, `WatchVocab.swift`, `WatchSpecText.swift`).

## Releases

The phone answers a watch's sync request in the reply (`sendMessage` with a reply
handler) and queues the same day with `transferUserInfo`; the watch says *iPhone
unreachable* only when `isReachable` is false.

The Apple Watch app is embedded in the phone app: `./ios/archive.sh` gives the watch
app and both widget extensions the phone's version and build, and one TestFlight
upload carries all four. On the tester's devices:

- TestFlight ▸ Training Companion ▸ *Automatic Updates* on, and the Watch app ▸
  General ▸ *Automatic App Install* on — then a phone update carries the watch app.
- If the watch app is missing, the phone says so (Settings ▸ Connections ▸ Apple Watch:
  *App not installed*); install it from the Watch app ▸ My Watch ▸ Available Apps.
- Up to 1.18.0 the watch listed the app as "TrainingCompanionWatch" (its display name),
  easy to miss when looking for Training Companion.

The Garmin app's version is `garmin/VERSION` (MAJOR.MINOR.PATCH, as `ios/VERSION`). The
manifest has none: it is typed into the store's upload form, which `build.sh --release`
(and `--demo`: the demo shares the app id and the sequence) prints with its tag,
`ciq-v<VERSION>`. A feature counts as shipped when both watches' releases carry it —
`ios-v…` and `ciq-v…`.
